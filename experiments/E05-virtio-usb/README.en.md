# E05: Ordinary VirtIO USB Device Contract for the Restore Kernel

This directory holds the contract specification and standalone self-authored ARM
guest fixture for this ordinary VirtIO device. It validates transparent byte
transport, modern VirtIO PCI, DMA, queue completion, and interrupts without
executing Apple firmware, requesting TSS, or treating fixture responses as Apple
USB ACKs or `restored` service responses.

The device required by the restore kernel is a separate path from booter BDIF
USB. In the pinned KernelCache, the `AppleVirtualPlatform` personality attaches
via PCI `106b:1a01` through
`AppleVirtIOPCITransport → AppleVirtIOUSBConfiguration → AppleVirtIOUSBDeviceController`.
The device is explicitly opt-in:

```text
-chardev socket,id=kernelusbr,path=<owned-socket>,server=on,wait=off
-device vmapple-virtio-usb-pci,chardev=kernelusbr
```

The implementation uses modern-only PCI and two split virtqueues, Q0 and Q1,
with a default ring size of 256; Q0 carries host→guest writable requests, and
Q1 carries guest→host read-only responses. The ring size is a local
implementation choice rather than misinterpreting the four 128KiB request
buffers pre-posted by the stock Apple guest as the ring size. No private USB
features are advertised; the fixture negotiates only `VIRTIO_F_VERSION_1`.

## Verified Ordinary Wire Fields

Outer framing on the host chardev is `u32 LE body_bytes + body`; this 4B length
prefix does not enter the guest descriptor chain. The request body upper bound
is `0x20000`, the response body is at least 2B, and the local implementation's
response capacity is 1MiB. The device forwards exact guest bytes without
fabricating Apple semantic responses.

| Body in guest queue | Layout |
| --- | --- |
| request | `u32 LE length@0, u8 endpoint@4, u8 type@5, payload@6` |
| response | `u8 type@0, u8 endpoint_or_value@1`, optionally followed by a separate payload descriptor |

The pinned source is `26A434/kernelcache.release.vma2`, uncompressed SHA-256
`ca55ea8c4c86170e870380ae5501b8b43adb2d2d3db28be4531b3040653be203`, fileset
`com.apple.driver.AppleVirtualPlatform`. All addresses below are unslid stock
code addresses; only instructions within named ordinary methods were inspected,
without resolving vtables, authentication objects, keys, or unknown indirect
targets.

| Field / Behavior | Named Method and Stock Address |
| --- | --- |
| Request is at least 6B; payload is `+6/-6` of buffer | `AppleVirtIOUSBRequestTransaction::getRequestHeader` `0xfffffe0008aa35f8`; `getRequest` `0xfffffe0008aa375c–379c` |
| type 1 transfer, type 2 reset, type 3 pause | `requestQueueEventHandler` `0xfffffe0008a8f840–f890` |
| Response fixed 2B header | `AppleVirtIOUSBResponseTransaction::transaction` `0xfffffe0008a94970–9497c` |
| Data response writes `type 1, endpoint` | `setDataResponse` `0xfffffe0008a94ab0–ab8` |
| Control response writes `type, endpoint_or_value` | `setControlResponse` `0xfffffe0008a94bf4–bf8` |
| Data segment starts at response offset 2 | `getBufferSegment` `0xfffffe0008a94c54–cd8` |

Non-isochronous OUT treats the header `length` as the inline data length and
verifies that it exceeds neither the payload nor the guest IO buffer capacity;
IN is distinguished by endpoint bit 7, copies no inline payload, and builds the
response using the guest IO's descriptors and length. The inspected IN branch
does not truncate responses by the host `length`, so that word must not be
treated directly as a maximum IN receive size. This is grounded in
`enqueuePendingRequestForTransaction` `0xfffffe0008a94394–43d0` and
`startNonIsocEndpoint` `0xfffffe0008a8f350–f3cc`.

EP0 follows separate rules: type 1 / endpoint 0 enters control handling, whereas
type 1 / endpoint `0x80` requests are rejected; guest EP0 IN is actively
generated by `startEp0In` with response byte 1 equal to 0 and can produce
zero-payload responses (`0xfffffe0008a8f190–f218`). `handleSetupRequest` reads
the leading 8B setup packet, and internal state 5/6 branches verify
`8 + wLength <= payload length` before copying `payload + 8`
(`0xfffffe0008a8ff50–ffcc`); no internal state enum names are inferred here.

Verified response types are: type 1 for data/OUT completion, type 2 for EP0
stall, type 3 for endpoint abort, type 4 for reset reply (second byte fixed at
`0x10`, enum meaning unconfirmed), and type 5 for endpoint pause reply.
`handlePauseEndpointRequest` clears only the host pending entries for that
endpoint (`0xfffffe0008a8fd94–fec8`); `handleAbortEndpoint` additionally clears
active guest IOs and moves them into the completion queue
(`0xfffffe0008a8e93c–eaac`). Only after a response is normally returned in the
used ring by the host does `responseQueueEventHandler` move the associated IO
into the completion queue (`0xfffffe0008a8f9dc–f9f8`), where `completeBuffers`
clears payload references (`0xfffffe0008a94e90`). Consuming data without
completing the virtqueue entry is not valid.

These are verifiable wire fields, not a complete USB/IP URB ABI. Per-URB
cancellation correlation and races, timeout/disconnect ordering, IN
chunk/short/ZLP policy, and the semantics of reset value `0x10` remain open. The
6B header carries no observed transfer-ID or standalone `errno32` field; no
unknown framing may be invented or extrapolated.

## Stock Driver Startup and Normal Activation

In the pinned kernel, `AppleVirtIOUSBConfiguration::start` is at
`0xfffffe0008a95220` and `AppleVirtIOUSBDeviceController::start` is at
`0xfffffe0008a8d898`; the latter directly calls
`IOUSBDeviceController::readyForHost` at `0xfffffe0008a8da3c`. Hitting these
entry points proves only matching and `start` execution—not queue creation, USB
descriptor configuration, or host enumeration.

Actual queue creation occurs inside `AppleVirtIOUSBDeviceController::goOnBus()`
`0xfffffe0008a8e00c–8a8e450`: Q0 and Q1 bind the request and response handlers
respectively, followed by pre-posting four 128KiB request buffers. The
`VERSION_1` check and feature/status negotiation also happen here. Consequently,
observing only `ACKNOWLEDGE` and zero queue addresses before entering this
method cannot be attributed to feature incompatibility; `config_size=0` and ring
size 256 remain local choices rather than native measurements.

Ordinary `IOUSBDeviceFamily` methods in the same stock KernelCache also
explicitly distinguish restore boot:

- `IOUSBDeviceConfigurator::start` (`0xfffffe00097295d8–97296b0`) checks for
  `-restore` at `9729614–9729628`; when present, it jumps to `9729694` and
  returns, skipping both the `DeviceDescription` read and the
  `createUSBDevice` call at `9729678`.
- `IOUSBDeviceController::readyForHost` (`9716b64–9716c74`) reads and converts
  `DeviceDescription`, calls `createUSBDevice` at `9716c18`, and then publishes
  the service; it neither checks that return value nor calls `goOnBus`
  directly. `createUSBDevice` (`9721c28–97241fc`) rejects a `NULL` description
  at `9721c68`.
- Normal `setProperties` / `gated_setProperties` recognizes `USBDeviceCommand`
  and `USBDeviceCommandParameter`; the `SetDeviceDescription` branch calls
  `createUSBDevice` at `97245c8`. Caller entitlement checks on this API remain
  intact and its implementation was not expanded.

This supports the explanation that restore mode waits for a normal configuration
call, without proving that a specific user-space process has launched, made the
call, or failed. Neither guest descriptions, configuration states, nor features
were force-set from the host.

Direct calls and pinned provenance for ordinary `CreateWithService`,
`DescriptionCreateFromControllerWithType`, and `SetDescription` in the stock
restore program are recorded under `restored_usb_startup_static` in
RAMDisk results, which serves as
the sole source of user-space static evidence. Runtime kernel observation uses
five independent one-shot points: pre-call and immediate return site of
`createUSBDevice` inside `readyForHost`, pre-direct-tail-call in
`SetDeviceDescription`, `startUSBStack` entry, and `goOnBus(bool)` entry. Only
the non-NULL description argument boolean, current `W0` at the return site, and
the `on_bus` boolean are recorded—no objects are dereferenced, and unpaired
pre-/post-call events are not treated as a successful single invocation.

## Self-Authored Guest Verification Entry Point

```sh
python3 -B experiments/E05-virtio-usb/run.py --build-only
python3 -B experiments/E05-virtio-usb/run.py --expect-binary-sha256 <main-confirmed-sha256>
python3 -B experiments/E05-virtio-usb/run.py --case q0-small --expect-binary-sha256 <main-confirmed-sha256>
```

`--build-only` compiles without running, and `--help` neither builds nor
launches a VM. A live run first verifies the binary digest in the current BDIF
build record and the presence of the opt-in device before creating a unique
`runs/e05-virtio-usb/<UTC>/` directory. The underlying QEMU source tree,
libraries, and BDIF binary are owned by the main line and are not modified by
this fixture.

`fixture.c` directly reuses the self-authored EL1 runtime, exception vectors,
and linker script from E06; it dynamically probes BAR sizes and the standard
modern capability chain on PCI slot 3, configuring common/notify/ISR regions,
feature/status registers, and Q0/Q1 from the discovered capability offsets.
Only standard PCI memory and bus-master enables are used. Slot 3 INTA routes
through GPEX index 3 to VMApple GIC input `0x23`, corresponding to **level
INTID 67**; the ISR reads-to-clear the VirtIO ISR register before writing EOIR,
and completion waits require observing the used index recorded by the ISR—DMA
or used-ring movement alone cannot substitute for an interrupt. In-guest waits
are bounded by counter deadlines, and a host timeout always fails. The machine
is configured with 4GiB / 2 CPUs / 24MHz exact, executing on CPU0 only with
16KiB-aligned allocations; PAC/CTRR protection semantics are out of scope here.

The positive sequence runs in four stages:

1. Pre-post Q0 with a writable SG chain consisting of a 6B header and a separate
   large payload buffer; the host splits the 4B outer prefix into 1/1/2B writes
   and fragments the body. The guest independently verifies type 1 / ep 4, the
   48B fixture payload, and canaries across the entire header/payload
   allocations, confirming real DMA together with used length 54 and IRQ 67.
2. Compute a 64B fixture response in the guest and submit it on Q1 via a 2B
   header and a separate read-only payload SG; the host checks the raw wire
   bytes byte-for-byte, and after waiting for used length 0 and IRQ delivery the
   guest verifies that inputs and guard pages remain unchanged.
3. Re-post Q0/Q1 with a 17B request and a 113B response, repeating data, used,
   ISR, and guard checks to verify normal acknowledgment and descriptor reuse
   without assuming a strict one-interrupt-per-command ratio.
4. Submit a 512KiB non-constant payload response from the guest. During this
   phase the host withholds socket reads for 2 seconds; for at least half a
   second the guest must observe neither Q1 used advancement nor completion ISR
   delivery, and the host additionally requires no guest large-response
   completion marker prior to its first socket read. Afterward, the host drains
   the entire wire payload byte-for-byte and requires used/IRQ completion plus
   read-only payload and guard checks to pass. This concretely distinguishes
   backpressured in-flight completion from data loss without mistaking internal
   buffering or a host timeout for completion.

The current runner also exercises read-only QMP diagnostics via production
`capture_virtio_devices(..., allow_usb=True)`: launching with `-S`, it queries
once in the stopped reset/prelaunch state, then resumes the guest to
`DRIVER_OK` prior to sending any fixture requests and queries a second time.
Both stages require USB internal `device-id` `0x100`, complete
host/guest/backend feature objects, two queues, and a live QEMU process after
the query. At reset `desc`/`used` must be 0, while at `DRIVER_OK` real
descriptor addresses must be populated with `VERSION_1` negotiated. Note that
this internal VirtIO ID (`0x100`) is distinct from PCI device ID `0x1a01`. Full
raw QMP replies are saved in `qmp.json` per run without reading guest MMIO or
ISR state.

Fixture traffic consists of real requests sent by the host and responses
validated and generated by the guest itself, read back as real wire bytes from
the host socket; the host never writes guest response memory. Raw wire captures,
UART/stderr logs, QMP replies, and structured JSON results are retained in the
same run directory, and both normal and failure paths reap the owned QEMU
process, close sockets, and remove temporary stub disks. No Apple sessions are
contacted, no GUI windows are opened, no physical USB devices are claimed, and
no pass claim is made for the stock Apple driver.

### QMP Diagnostic Regression for Internal ID `0x100`

When stock-kernel integration first invoked `x-query-virtio-status`, the QMP
feature decoder lacked a registration for internal ID `0x100`, triggering a host
`assert`/`abort`; execution had not yet reached `bootx`, so that crash could not
be interpreted as a USB datapath failure. The
original failure log
is retained. Within patch 0015 on the main line, internal ID `0x100` was
registered as transport-features-only while leaving unknown private bits marked
unknown, without altering the device datapath.

The resulting binary SHA-256 is
`5ae35ab669adb8e00418d51481e88679ded777c91fe79c0c9a353f8149ece6dd`.
A single updated positive run
passed directly while keeping the earlier `df44` positive and negative artifacts
intact and without rerunning the `q0-small` negative case. The self-authored
guest firmware retained the identical `2c8030…acab` digest. Production queries
at both reset/prelaunch and `DRIVER_OK` returned `device-id` 256, all three
feature objects, and queues 0/1: `dev-features` empty, host advertising only
`INDIRECT_DESC`/`EVENT_IDX`/`VERSION_1`, guest negotiating only `VERSION_1`, and
backend empty. At reset both queues reported `desc`/`used` equal to 0; after
launch both `desc` addresses were non-zero with `DRIVER_OK` set; `query-status`
responded before and after with QEMU alive and zero assertions. Raw replies are
recorded in QMP log.
Both rounds of real SG/DMA/IRQ 67/guard checks and the 512KiB backpressure phase
also passed on this binary (host read delayed 2.0081s with no premature
completion; guest exit 0, process reaped, temporary directories cleaned). This
verifies the diagnostic regression for the observed failure alongside the same
positive datapath, without claiming coverage over a matrix of unknown private
feature bits.

### Independent Integration with the Stock Kernel

This narrowed the remaining gap to ordinary descriptor submission / activation
and downstream steps; under the static startup contract documented above,
staying in `ACKNOWLEDGE` before entering `goOnBus` cannot be attributed to

the clean exit from run `-02` are preserved separately without mislabeling
