# 后台负载对 Safari 首个 GPU 连接初始化时间的影响（Run141 起）

日期：2026-11-11 UTC 起。本文件的"计划"一节在运行之前提交。

## 运行前写下的计划

### 起因

Run140 的宿主采样显示，从启动后 90 秒到关机，客体的 8 个 vCPU 几乎一直全忙，忙的主要是登录后用户会话的后台工作；没有登录时（Run138）平均只有 2.3 个 vCPU 在忙。到目前为止的 16 个初始化时间样本，都是在这种负载下取得的。见[宿主 CPU 报告](M3-GPU-INIT-HOST-CPU-USE.md)。

### 假设

初始化时间被登录后的后台工作拉长了。等客体安静下来再启动 Safari，开机后第一次启动的初始化时间会低于 3.0 秒。

### 步骤

- 配置与 Run132、134、136 相同：QARMA5 加 memo，4 GiB，带 30 秒诊断。宿主线程采样器和时钟监听在后台运行。
- 登录后在终端里运行 `caffeinate -dimsu -t 5400 &`，防止长时间无人操作时锁屏。
- 每分钟算一次上一分钟的 `vcpu_mean_busy`。连续三个一分钟都低于 3.0 算"安静"。时限是启动后 2700 秒。
- 一旦安静或到了时限：执行与以前相同的试验前准备（确认 Safari 未运行、核对身份、武装诊断、时钟探针、预先键入命令），准备结束后 240 秒按回车做第一次试验；再过 300 秒做第二次试验；然后导出日志窗口、关机。

### 判定

主指标是第一次试验的 `ui_request_to_did_initialize`。此前所有第一次启动的样本在 3.444–3.791 秒之间（7 个，含 8 GiB 的一个）。

| 情形 | 条件 | 含义和下一步 |
|---|---|---|
| 支持 | 到达安静，按回车前 25 到 5 秒的基线低于 3.0，初始化低于 3.0 秒 | 后台争用是主要原因。下一轮在安静的客体上去掉诊断，按原始 3 秒期限测首次加载 |
| 部分 | 到达安静，基线低于 3.0，初始化在 3.0 到 3.444 秒之间 | 后台有影响，但不足以解释全部。结合窗口内的 `vcpu_mean_busy` 和阻塞采样再定 |
| 否定 | 到达安静，基线低于 3.0，初始化不低于 3.444 秒 | 后台争用不是主要原因。转向 QEMU 一侧：vCPU 线程的阻塞时间和函数级剖面 |
| 未检验 | 到时限仍未安静，或基线不低于 3.0 | 试验照做，作为 4 GiB 下带采样的参照；报告后台负载至少持续了多久。下一步考虑在试验期间暂停后台进程 |

无论哪种情形都报告：后台负载随时间的变化、到达安静所用的时间、窗口内的 `vcpu_mean_busy`。

### 探索性记录（不参与判定）

Run140 里，"全忙"的 vCPU 线程也有约 22% 的时间被阻塞，原因不明。本次会话 `sudo -n` 可用，所以顺带记录：

- 阻塞采样：以 root 每 10 毫秒读一次 8 个 vCPU 线程的 `/proc/PID/task/TID/syscall`，得到线程是在运行，还是阻塞在哪个系统调用、哪个 futex 地址上；地址按 QEMU 二进制的符号表归到 `bql`、`exclusive_resume` 等。这个接口不暂停线程。在等待期间的饱和阶段做一次 40 秒，安静之后做一次 40 秒，第二次试验的初始化窗口前后做一次 70 秒。
- perf 采样：饱和阶段和安静之后各 15 秒（`perf record -F 499 -g -p PID`）。

第一次试验期间不做这两种采样，只有与 Run140 相同的线程计数采样在运行。

### 已知的限制

- 只有一轮、一个主样本。
- "安静"和"开机更久"分不开：等得越久，文件缓存越热，内存状态也不同。
- 第二次试验期间有 root 采样在运行，它的数字只作参考。
- 等待期间客体持续高负载，宿主温度照常记录。

### 运行前修订（2026-11-12，Run141 中断之后、任何试验之前）

Run141 在启动后 672 秒被终止，没有试验。当时我的一条命令被中断，控制器随之收到 SIGTERM 并结束了 QEMU（`teardown=terminate`，QEMU 退出码 0）。客体登录后只过了 6 分半钟，一直是饱和的（每分钟的 `vcpu_mean_busy` 为 5.1–5.8）。重跑用 Run142，加 `--allow-unclean-storage`，其余不变。

终止之前，计划里的探索性采样已经做了两次，都在饱和阶段。8 个 vCPU 线程的采样点分布如下：

| | 第一次（启动后 490–530 秒，40 秒） | 第二次（657–672 秒，15.5 秒，带调用栈） |
|---|---|---|
| 在运行或可运行 | 78.4% | 74.3% |
| 等 QEMU 全局锁（`bql`） | 16.6% | 8.8% |
| 等别的 vCPU 的独占段结束（`exclusive_resume`） | 4.0% | 14.3% |
| 自己发起独占段、等其他 vCPU 停下（`exclusive_cond`） | 0.5% | 2.1% |
| 等 `qemu_cpu_list_lock` | 0.6% | 0.5% |
| 空闲（停在自己的 halt 条件变量上） | 0.0% | 0.0% |

这解释了 Run140 里"全忙时每个 vCPU 也只有约 76% 的时间在宿主 CPU 上"：其余时间不是空闲，而是卡在 QEMU 自己的两种同步上。调用栈显示，发起独占段的几乎都是排队的"安全工作"（`process_queued_cpu_work` → `start_exclusive`），栈里同时出现 TLB 范围刷新的函数，所以来源很可能是客体的广播式 TLB 失效指令，QEMU 把它实现成让所有 vCPU 停下。等全局锁的位置主要是 vCPU 线程每次退出执行循环后重新取锁（`mttcg_cpu_thread_fn`），其次是读带 IO 标记的系统寄存器（`helper_get_cp_reg64`）和处理中断。两种阻塞的比例随时间变化很大，两次采样合计都在 21%–26%。

这些是探索性结果，不改变本计划的假设和判定。采样文件在 `runs/e05-installed-boot/m3-gpuinit-quiet-qarma5-20261111-141/`（`vcpu-block-saturated.txt`、`vcpu-block-saturated-stacks.txt`、`perf-saturated.data`）。

## 结果（Run142）

### 结论

按判定表，结果是**部分**：客体安静下来之后，开机后第一次启动 Safari 的初始化是 3.249 秒，低于此前所有第一次启动的样本（3.444–3.791 秒），但没有低于 3.0 秒。

更重要的是原因：**按回车前客体是安静的，初始化窗口却照样饱和**。Safari 的启动自己就把 8 个 vCPU 占满了。所以"等后台消退"只能去掉一部分争用，去不掉启动本身造成的那部分。而在这种饱和下，vCPU 线程有一成到四分之一的时间卡在 QEMU 自己的全局锁上。

### 后台负载多久消退

登录在启动后 162 秒。此后每分钟的 `vcpu_mean_busy` 在 4.9–6.1 之间，持续到第 20 分钟；第 21 分钟降到 3.6，第 22 分钟起是 1.3–2.4。连续三分钟低于 3.0 的条件在启动后 1512 秒满足。也就是说，登录后的后台工作在这个模拟速度下要跑约 20 分钟。宿主封装温度随之从 80–87 °C 降到 52–54 °C。

Run131–140 的全部试验（启动后 12 到 28 分钟）都落在这段时间之内或刚过。

### 两次试验

| | 第一次启动 | 第二次启动 |
|---|---|---|
| 按回车的时刻（启动后） | 1836 秒 | 2136 秒 |
| 按回车前 25 到 5 秒的基线 `vcpu_mean_busy` | 1.28（92% 的时间只有一个或零个 vCPU 在忙） | 1.47 |
| `ui_request_to_did_initialize` | **3.249 秒** | **2.588 秒** |
| 此前同类样本的范围（负载下） | 3.444–3.791 秒（7 个） | 2.768–3.419 秒（7 个） |
| 四个分段 | 1.788 / 0.253 / 0.762 / 0.390 秒 | 1.437 / 0.108 / 0.829 / 0.210 秒 |
| 窗口内的 `vcpu_mean_busy` | 5.96（8 个全忙占 89%） | 6.13（91%） |
| GPU 进程出现到连接请求之间（约 34 秒） | 5.15（全忙 67%） | 5.06（全忙 66%） |
| 观察脚本启动到 GPU 进程出现 / 到首个 GPU 请求 | 51.6 / 85.4 秒 | 27.8 / 61.3 秒 |
| 试验期间的压缩 / 解压次数 | 68496 / 48781 | 24427 / 23851 |

- 两次试验都完成了初始化，Safari 的 GPU 进程无响应退出 0 次。
- 两次试验期间各有三个 GPU 进程：除 Safari 的之外，两个 `nsattributedstringagent` 实例也在用 WebKit，各自启动了 web 进程和 GPU 进程，它们的 GPU 连接初始化用了 2.7–4.3 秒。Run131–140 的试验里只有 Safari 的一个 GPU 进程。这些后台任务看来是等系统空下来才开始的，结果正好与 Safari 的启动重叠。诊断点 site0 因此共命中 6 次。
- 启动路径（观察脚本启动到首个 GPU 请求）比负载下只快了 7%（85.4 对平均 92.1 秒），也说明启动本身是受 CPU 限制的。
- 客体自己关机，控制器记录为客体关机（退出码 0）。全程 41 分钟，封装温度最低 52、平均 77.1、最高 91 °C。

### vCPU 线程卡在哪里（探索性）

| 时段 | 在运行或可运行 | 空闲 | 等全局锁 `bql` | 等独占段 |
|---|---|---|---|---|
| 饱和阶段（启动后 419–459 秒） | 81.0% | 0.0% | 14.8% | 3.6% |
| 安静阶段（准备之后，40 秒） | 20.0% | 78.7% | 0.8% | 0.5% |
| 第二次试验：连接请求之前的 20 秒 | 70.5% | 0.0% | 26.0% | 3.1% |
| 第二次试验：初始化窗口（2.6 秒） | 86.4% | 0.0% | 10.2% | 2.8% |

加上 Run141 的两次采样（见上面的修订），结论一致：只要客体忙起来，vCPU 线程就有 14%–30% 的时间在等 QEMU 的同步，其中全局锁通常占大头。调用栈里，等全局锁的位置依次是 vCPU 线程退出执行循环后重新取锁（`mttcg_cpu_thread_fn`，约一半）、读带 IO 标记的系统寄存器（`helper_get_cp_reg64`）、处理中断和排队工作。独占段来自排队的"安全工作"，QEMU 用它实现客体的广播式 TLB 失效（`tlb_flush_*_all_cpus_synced`）：每执行一次，所有 vCPU 都要停下。

Safari 启动期间这个比例最高（26%）。启动要创建很多进程，进程的创建和退出正是 TLB 失效、核间中断和系统寄存器访问最密集的时候。

### 顺带修正

`gpu_init_timing.py` 以前用"下一个 GPU 进程出现"作为第一个 GPU 进程事件的截止点，不管那个进程属于谁。Run142 里别的客户端的 GPU 进程出现在 Safari 的请求之前，脚本于是报告"没有连接请求"。现在只有同一属主的下一个 GPU 进程才算截止点，并补了回归测试。修正前的两份输出保留为 `superseded-timing-*.json`。

### 证据

- `runs/e05-installed-boot/m3-gpuinit-quiet-qarma5-20261112-142/`：采样、时钟探针（两次相差 4.4 毫秒）、`gpu-init-cpu-profile-*.json`、`vcpu-block-saturated.txt`、`vcpu-block-quiet.txt`、`vcpu-block-trial2.txt`、`perf-saturated.data`、`perf-quiet.data`、两个日志窗口。
- `runs/quiet-guest-gpu-init-20261112/`：`trials-run142.json` 和驱动脚本（`driver/`，含阻塞采样器 `block_sampler.py` 和汇总脚本 `block_report.py`）。

### 限制

- 只有一轮。3.249 和 2.588 秒各是一个样本；它们低于此前的范围，但差别不大，不足以单独证明后台负载的影响有多少。
- "安静"与"开机更久"分不开，这一点没有变。
- 两次试验都与 `nsattributedstringagent` 的 WebKit 活动重叠，没有得到真正无干扰的窗口。
- 阻塞采样的调用栈是扫描线程栈上的返回地址得到的，离锁最近的那个函数可靠，更外层的可能有误。阻塞采样器和汇总脚本还在证据目录里，没有收进仓库，也没有测试。
- 第二次试验期间有 root 采样在运行。

### 下一步

初始化窗口无论如何都是饱和的，而饱和时最大的一块可回收的损失在 QEMU 里。下一步是量出全局锁和独占段各由哪些客体操作触发（按系统寄存器、退出原因和 TLB 失效指令计数），再针对最多的几项做补丁：让广播式 TLB 失效不必停下所有 vCPU，让常见的退出原因不必经过全局锁。
