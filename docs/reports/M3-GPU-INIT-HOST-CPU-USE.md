# Safari 首个 GPU 连接初始化期间，宿主 CPU 在做什么（Run138 起）

日期：2026-11-11 UTC 起。本文件的"计划"一节在运行之前提交。

## 运行前写下的计划

### 问题

Run132–137 表明，开机后第一次启动 Safari 时，首个 GPU 连接的初始化要 3.5 到 3.8 秒，而且不随 PAC 算法变化，尽管更快的算法让整条启动路径快了 11% 到 21%（见 [PAC 算法对比](M3-PAC-ALGORITHM-GPU-INIT-TIMING.md)）。要决定下一步优化什么，先得知道这 3.5 秒里系统是在计算，还是在等待。

### 方法

这台宿主对普通用户关闭了 perf（`perf_event_paranoid=4`），本会话又没有 root，所以不用 perf，改用调度器自己的线程计数：

- `host_thread_sampler.py` 每 10 毫秒读一次 QEMU 所有线程的累计在 CPU 时间、排队等待时间和最近所在的宿主 CPU。它只读 `/proc`，不附着到 QEMU。
- `clock_offset.py` 让客体把自己的时钟读数发给宿主，得到两边时钟的差，精度几毫秒。
- `gpu_init_cpu_profile.py` 用这个时钟差，把 WebKit 日志里各事件的时刻对到宿主的采样上。

客体的 vCPU 空闲时，对应的宿主线程在睡眠，所以 vCPU 线程的在 CPU 时间能反映客体在不在计算。报告同时给出窗口前后各 10 秒的数字作参照。

### 指标

`vcpu_mean_busy`：一段时间内平均有多少个 vCPU 线程在宿主 CPU 上运行（8 个 vCPU，取值 0 到 8）。主指标取初始化窗口（Safari 记录连接请求，到它记录 `didInitialize`）和窗口里三个较长的分段，用开机后第一次启动的那次试验。第二次启动的试验作为重复。

### 判定

| 情形 | 条件 | 含义和下一步 |
|---|---|---|
| 等待为主 | 窗口里有一个 0.5 秒以上的分段，`vcpu_mean_busy` 低于 0.5 | 那一段客体基本空闲，时间花在等待上。下一步找出等的是什么 |
| 串行计算 | 窗口整体在 0.5 到 2.0 之间，且没有分段低于 0.5 | 一条串行的链在执行，受单线程模拟速度限制。下一步看这条链有多少时间落在能效核上，并取得函数级的剖面 |
| 并行未饱和 | 窗口整体在 2.0 到 6.0 之间 | 多个线程同时在跑。结合能效核占比和排队等待再定 |
| 饱和 | 窗口整体在 6.0 以上 | vCPU 不够用。下一步试更多 vCPU |

三个较长的分段是：GPU 进程收到请求到激活 AudioComponentRegistrar 连接（此前为 1.6–2.0 秒）、SandboxHelper 连接从创建到销毁（约 1.0 秒）、销毁到 `didInitialize`（第一次启动约 0.55–0.7 秒）。

### 同时记录

- vCPU 的在 CPU 时间里，落在能效核上的比例。宿主有 8 个性能核（CPU 0–7）和 12 个能效核（CPU 8–19），QEMU 的线程没有绑核。
- vCPU 线程可以运行却没有拿到宿主 CPU 的时间。
- 主线程和其他 QEMU 线程的在 CPU 时间。
- 采样的最长间隔，用来判断采样有没有卡顿。
- 两次时钟探针（第一次试验之前、第二次试验之后）结果的差。

### 配置与步骤

配置与 Run132、134、136 相同：QARMA5 加 memo，带 30 秒诊断。另加 `--allow-unclean-storage`，因为 Run137 的收尾记录是在控制器修正之前写的。

步骤也相同（第一次试验在启动后 720 秒触发，第二次在 1020 秒），只多三件事：采样器和时钟监听在后台运行；武装诊断之后执行一次时钟探针；第二次试验之后再执行一次。

这一轮顺带给这个配置增加一对初始化时间样本。此前的范围是第一次启动 3.515–3.791 秒、第二次启动 2.768–3.419 秒。如果新样本明显落在范围之外，说明采样或探针干扰了被测对象，结果要打折扣。

### 已知的限制

- 采样看到的是宿主线程，不是客体进程。窗口里 vCPU 在忙的是 GPU 进程、辅助进程，还是无关的后台工作，这个方法分不出来。
- 只有一轮、两次试验。数字用来在上面几种情形之间做选择，不用来比较小的差别。
- 调度统计的分辨率是 1 毫秒，采样间隔 10 毫秒。最短的分段约 0.2 秒，误差可以到 5%。
- 时钟差的估计里含有网络传输的最小延迟，偏差在几毫秒以内。

## 运行前修订（2026-11-11，Run138 中断之后、任何试验之前）

### Run138 没有试验数据

Run138 在启动后 662 秒被终止：上一个会话结束，控制器、QEMU 和三个后台记录都收到了信号，`qmp-lifecycle.json` 记录的是 `SHUTDOWN reason=host-signal`。当时客体停在登录窗口，还没有登录，也没有做任何试验。下一轮仍要加 `--allow-unclean-storage`。

### 这 11 分钟的采样说明了什么

- 工具可用。65830 次采样，间隔的中位数是 10.0 毫秒，最长 11.9 毫秒；按线程名找到的 8 个 vCPU 线程与控制器记录的线程号一致。
- 客体没人操作时也不空闲。停在登录窗口的 5 分钟里（启动后 300–600 秒），`vcpu_mean_busy` 是 2.3，单个 10 秒片段到过 2.6。开机阶段（60–150 秒）是 5.5，其中 74% 的时间 8 个 vCPU 全忙。
- 负载低的时候，vCPU 有一半时间跑在能效核上：登录窗口阶段能效核占 vCPU 在 CPU 时间的 51%，开机阶段是 12%。

### 判定表的缺陷和修订

原来的判定表默认客体空闲时 vCPU 接近全闲。实际上后台工作本身就占着两个多 vCPU，Safari 启动期间还有 Safari 主进程和 web 进程自己的计算。所以窗口里的 `vcpu_mean_busy` 不可能低到 0.5，"等待为主"和"串行计算"两格按原来的阈值不会出现。宿主采样也分不清在忙的是谁，这一点原计划已经列为限制。

修订后，宿主采样只回答它能回答的问题：窗口里 CPU 供给够不够。

| 情形 | 条件 | 含义和下一步 |
|---|---|---|
| 饱和 | 窗口整体的 `vcpu_mean_busy` 在 6.0 以上，或者窗口里至少一半时间有 7 个以上 vCPU 在忙 | CPU 供给是限制。下一步试更多 vCPU、把 vCPU 绑到性能核，或减少后台工作 |
| 不饱和 | 其余情况 | CPU 供给不是限制。初始化是一条跨进程的串行链，继续从客体侧找每一步在等什么 |

同时报告试验前的基线：按下回车之前 25 秒到 5 秒这一段的 `vcpu_mean_busy`（按宿主时间取，不依赖时钟探针），以及各段的能效核占比。

"计算还是等待"改由客体侧的记录回答。旧存档里已经有 GPU 进程各线程的累计 CPU 时间，结论是 GPU 进程在窗口内主要在等别的进程，见[内存大小对照](M3-RAM-SIZE-GPU-INIT-TIMING.md)的"起因"一节。

### 顺序调整

旧存档同时显示 4 GiB 的客体内存一直处在压力之下。所以下一轮先做 8 GiB 的内存对照（Run139 起），采样器和时钟探针照常运行，并按上表报告。4 GiB 下带采样的那一轮是否还需要，等内存对照有了结论再定。

## 结果（Run140，8 GiB）

### 结论

按修订后的判定表，结果是**饱和**：初始化窗口里 8 个 vCPU 有约 90% 的时间全部在忙。而且不只是窗口，从启动后 90 秒到关机，客体几乎一直是这个状态，包括桌面上没有人操作、只等着按回车的那几分钟。CPU 供给是限制。

这一轮用的是 8 GiB（见[内存大小对照](M3-RAM-SIZE-GPU-INIT-TIMING.md)），4 GiB 下没有带采样的运行。

### 数字

| 区间 | 第一次启动 | 第二次启动 |
|---|---|---|
| 初始化窗口的长度 | 3.444 秒 | 3.061 秒 |
| 窗口的 `vcpu_mean_busy` | 6.03 | 6.16 |
| 窗口内 8 个 vCPU 全忙的时间占比 | 90% | 92% |
| 窗口内每个 vCPU 的在 CPU 时间 | 2.54–2.65 秒 | 2.29–2.44 秒 |
| 窗口内能效核占 vCPU 时间的比例 | 6% | 2% |
| 窗口内 vCPU 排队等宿主 CPU 的时间（8 个合计） | 0.66 秒 | 0.94 秒 |
| 按回车前 25 到 5 秒的基线 | 6.19（全忙 91%） | 6.08（全忙 66%） |
| 请求前 10 秒 | 4.31 | 4.90 |
| `didInitialize` 后 10 秒 | 5.42 | 5.86 |

窗口内的各分段都在 6.1–6.5 之间，只有最后一段（SandboxHelper 连接销毁到 `didInitialize`）是 4.9。

整轮运行按 30 秒一格看：从启动后 90 秒到第二次试验结束（约 1160 秒），`vcpu_mean_busy` 大多在 5.3–6.4 之间，8 个 vCPU 全忙的时间占 55%–96%。低于这个水平的有三处：登录前后（180–240 秒，4.9–5.3）；每次试验开始后 Safari 刚启动的半分钟（按 2 秒一格看最低到 2.8–3.6，其间约一半时间只有一个或零个 vCPU 在忙）；第二次试验结束之后到关机（4.6–5.6，全忙 21%–60%）。

### 怎么读这些数字

- **"全忙"时每个 vCPU 也只有约 76% 的时间在宿主 CPU 上。** 排队等宿主 CPU 的时间只占约 2%，所以剩下的约 22% 里 vCPU 线程是被阻塞的，不是抢不到宿主 CPU。采样分不出它们被什么阻塞。`vcpu_mean_busy` 6.0 左右就是 8 个 vCPU 的上限，而不是还有两个空着。
- **饱和时 vCPU 已经在性能核上。** 窗口内能效核只占 2%–6%；负载低的时候才会到 30%–50%（请求前 10 秒是 33%，Run138 的登录窗口是 51%）。所以把 vCPU 绑到性能核对饱和的窗口帮助不大。
- **忙的主要是后台。** 运行结束时（开机 20 分钟）还活着的近 600 个进程累计用了约 7300 秒 CPU，不含已退出的进程和内核线程。这些时间分散在几百个进程里：WindowServer 337 秒、launchd 278 秒、Siri AI 250 秒、dasd 197 秒、Terminal 183 秒、mobileassetd 161 秒、softwareupdated 140 秒、mediaanalysisd 132 秒、corespotlightd 119 秒等。相比之下，Run138 没有登录，停在登录窗口时只有 2.3。也就是说，登录后用户会话的后台工作在 TCG 下持续占满 8 个 vCPU，至少 20 分钟。
- **初始化本身是一条跨进程的串行链。** GPU 进程的主线程自己用的 CPU 不超过窗口长度的一半（这是上限，算法见内存对照报告），其余时间在等 tccd、coreaudiod、AudioComponentRegistrar 和新启动的 SandboxHelper；后者是纯计算（见内存对照报告）。这条链是在一个已经被后台占满的客体上执行的。

### 工具本身

- 采样 135463 次，覆盖 1354.6 秒，窗口内最长的采样间隔是 10.3 毫秒。
- 两次时钟探针（武装诊断之后、第二次试验之后，相隔 14 分钟）得到的时钟差是 −1.615117 和 −1.619839 秒，相差 4.7 毫秒；各自 12 个读数的离散是 7.6 和 2.0 毫秒。中间执行过一次诊断读数（会短暂暂停虚拟机），没有造成可见的偏移。
- 初始化时间（3.444、3.061 秒）落在此前的范围附近，没有迹象表明采样或探针干扰了被测对象。

### 证据

`runs/e05-installed-boot/m3-gpuinit-ram8g-qarma5-20261111-140/`：`host-threads.tsv`（采样）、`clock-offset.jsonl`、`gpu-init-cpu-profile-r140safari.json` 和 `-r140safarib.json`（各区间的完整数字）、`driver-return1.txt` 和 `driver-return2.txt`（按回车的宿主时刻）。Run138 的采样在它自己的运行目录里。

### 限制

- 只有一轮，而且是 8 GiB。4 GiB 下后台负载至少同样重，但没有直接测过。
- 宿主采样看不到客体进程。"后台占满"的依据是运行结束时的累计 CPU 时间，不是窗口内的逐进程采样。
- 约 22% 的阻塞时间原因不明，需要函数级或调度事件级的剖面。

### 下一步

饱和把问题变成了两个可以分别检验的方向：

1. 减少对 CPU 的争用。先看登录后的后台工作多久才会消退，以及在客体安静下来之后启动 Safari，初始化时间是多少。
2. 找出 vCPU 线程那 22% 的阻塞时间花在哪里。这需要 perf；本次会话里 `sudo -n` 可用。

两项都在 Run141、142 做了，结果见[安静客体报告](M3-QUIET-GUEST-GPU-INIT-TIMING.md)：后台负载约 20 分钟后消退，但 Safari 的启动自己就会让窗口饱和；阻塞时间花在 QEMU 的全局锁和独占段上。
