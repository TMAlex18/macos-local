# 客体内存大小对 Safari 首个 GPU 连接初始化时间的影响（Run139 起）

日期：2026-11-11 UTC 起。本文件的"计划"一节在第一轮运行之前提交。

## 运行前写下的计划

### 起因

Run138（[宿主 CPU 采样](M3-GPU-INIT-HOST-CPU-USE.md)）在登录之前被打断，没有试验数据。重跑之前，我整理了 Run131–137 的 14 次试验存档里已有、此前没有用过的客体侧记录（`runs/ram-size-gpu-init-20261111/trials-4gib-runs131-137.json`），得到三点。

1. **客体内存一直是满的。** 每次试验开始前，4 GiB 的客体只剩 57–68 MiB 空闲页（有一次是 210 MiB），压缩器里存着 1.3–2.2 GiB 的数据。一次试验约 145 秒，期间内核新增 3.4 万到 10.6 万次页压缩（每页 16 KiB，合 0.5–1.6 GiB）、3.1 万到 6.8 万次解压、1.3 万到 6.3 万次从磁盘读入。交换文件没有用到。
2. **初始化时间与压缩次数一起变化。** Run132–137 的 12 次试验里，初始化时间与试验期间压缩次数的相关系数是 0.81，与解压次数是 0.73。这是事后的观察，而且与"第几次启动"混在一起：第二次启动更快，压缩也更少。
3. **窗口里 GPU 进程自己很少在计算。** 以 Run136 的第一次试验为例，3.727 秒的窗口里，GPU 进程的主线程在依次初始化音频：CoreAudio 和语音处理的准备约 0.2 秒，向 tccd 查询麦克风权限 0.2 秒，CoreAudio HAL 0.9 秒，偏好设置和 CoreServices 0.45 秒，连接 AudioComponentRegistrar 0.27 秒，SandboxHelper 连接从创建到销毁 1.06 秒；此后 0.6 秒 Safari 记录 `didInitialize`。而探针每隔几秒记录的 `ps -M` 显示，在一段包住窗口的 13–44 秒里，这个主线程总共只用了 0.76–1.17 秒 CPU，相当于窗口长度的 18%–39%。所以窗口的大部分时间，GPU 进程在等别的进程答复。

内存紧张时，长期空闲的服务进程的页会被压缩，被叫醒时要先解压；新进程（如 SandboxHelper）要的内存也得靠压缩别的页腾出来。压缩和解压在 TCG 下都很慢。所以内存压力是"等别的进程"的一个具体的可能原因，而且可以直接检验。

以前的两次 8 GiB 对照（Run89、Run97）只看页面能不能显示，没有量过这个时间。Run89 在原始 3 秒期限下首次加载成功，当时的报告认为单次观察不足以说明原因。

### 假设

4 GiB 下的内存压力拉长了首个 GPU 连接的初始化。把客体内存改成 8 GiB，试验期间不再大量压缩，初始化时间明显变短。

### 指标与判定

主指标仍是 `ui_request_to_did_initialize`，取开机后第一次启动 Safari 的那次试验。4 GiB 的参照是 Run132–137 的六个样本：3.515–3.791 秒。两种 PAC 算法在这个指标上没有差别，所以合并使用。

先做两轮 8 GiB（Run139、Run140）。

| 结果 | 条件 | 下一步 |
|---|---|---|
| 支持 | 两轮的第一次启动都低于 3.515 秒。如果内存大小没有影响，出现这种情况的概率是 1/28 | 两轮都低于 3.0 秒时，下一轮在 8 GiB 下去掉诊断，按原始 3 秒期限测首次加载；否则报告缩短了多少，再回到宿主 CPU 的分析 |
| 否定 | 两轮都不低于 3.515 秒 | 内存大小不是决定因素。回到 4 GiB，做带宿主采样的那一轮 |
| 不确定 | 一轮低于，一轮不低于 | 再做一轮 8 GiB 和一轮当天的 4 GiB 对照 |

操作检验有两条：试验记录的 `hw.memsize` 约为 8.58×10⁹；第一次试验期间的压缩次数低于 7578，即 4 GiB 下第一次启动最小值 75776 的十分之一。如果 8 GiB 下客体仍然大量压缩，这一轮就没有检验到假设，按"操作无效"报告，不套用上表。

次要指标：第二次启动（4 GiB 参照 2.768–3.419 秒）、窗口的四个分段、观察脚本启动到首个 GPU 请求的时间、GPU 进程主线程的 CPU 时间上限、宿主侧的 `vcpu_mean_busy`。

### 配置与步骤

配置与 Run132、134、136 相同（QARMA5 加 memo，带 30 秒诊断），只把 `--ram-gib 4` 换成 `--ram-gib 8`。Run139 另加 `--allow-unclean-storage`，因为 Run138 是被信号终止的。步骤也相同：第一次试验在启动后 720 秒触发，第二次在 1020 秒。

与 4 GiB 参照相比，另有三处不同，都与内存无关：

- 宿主线程采样器和时钟监听在后台运行。采样器只读 `/proc`。
- 武装诊断之后、第二次试验之后各执行一次时钟探针。一次探针是约 3 秒的 TCP 往来，第一次在第一次试验前至少一分钟结束。
- 第二次试验之后、关机之前，客体用 `guest-diag/log-window.sh` 导出两个初始化窗口里全部进程的系统日志、launchd 日志的相应片段、一份进程列表和内存压力摘要。每个窗口最多等 220 秒，拿不到就照常关机。这一步在两次试验都结束之后，不影响指标。

### 已知的限制

- 4 GiB 的参照是约 12 小时前取得的，没有与 8 GiB 交替进行。温度和宿主负载的差别只做记录，没有控制。
- 每个条件的样本很少，判定规则只能分辨大的差别。
- 数字都在 30 秒诊断下取得，不等于原始期限下的行为。
- 8 GiB 改变的不只是压缩：文件缓存更大，系统的后台工作也可能不同。指标变化只说明内存大小有影响，具体机制要靠内存计数和日志判断。

### 运行前修订（2026-11-11）

Run139 这个编号没有产生运行。控制器在启动 QEMU 之前就拒绝了，因为 Run138 被信号中断后留下的临时链接还没有清理；磁盘没有被打开。用 `recover-abandoned.py --run m3-gpuinit-hostcpu-qarma5-20261111-138` 清理之后，两轮 8 GiB 改用 Run140 和 Run141 的编号，其余不变。

## 结果

### 结论

8 GiB 没有明显缩短初始化，内存压力不是这 3.5 秒的主要原因。这个结论来自一轮运行（Run140），按计划里的条款它属于"操作无效"：8 GiB 下客体仍在压缩内存，只是少了很多。所以没有套用判定表，也没有做第二轮。

### Run140 的数字

| | 4 GiB（Run132–137） | 8 GiB（Run140） |
|---|---|---|
| 第一次启动的初始化时间 | 3.515–3.791 秒（6 个样本） | 3.444 秒 |
| 第二次启动的初始化时间 | 2.768–3.419 秒（6 个样本） | 3.061 秒 |
| 第一次试验期间的压缩次数 | 75776–105748 | 30381 |
| 第一次试验期间的解压次数 | 49450–62632 | 11410 |
| 第一次试验期间从磁盘读入的页数 | 32618–38322 | 29168 |
| 第二次试验期间的压缩 / 解压次数 | 34145–85631 / 30898–60466 | 18023 / 5914 |
| 试验前压缩器里的数据 | 1.3–2.0 GiB | 0.26 GiB、0.52 GiB |
| 试验前的空闲页 | 57–68 MiB（一次 210 MiB） | 66 MiB、63 MiB |

- `hw.memsize` 是 8579448832，客体确实看到了 8 GiB。`memory_pressure` 报告的系统空闲比例是 88%。空闲页仍然只有 60 多 MiB，是因为 macOS 把多出来的内存都用作文件缓存。
- 第一次试验期间的压缩次数是 30381，高于操作检验的上限 7578，所以这一轮不算干净的"无压缩"条件。但压缩少了 60%–71%，解压少了 77%–82%，初始化时间只比 4 GiB 的最小值低 0.07 秒，比 4 GiB 的平均值（3.66 秒）低 0.22 秒。如果压缩和解压是主要原因，时间应该跟着大幅下降。计划"起因"里的相关系数 0.81，主要反映的是第一次和第二次启动的差别。
- 四个分段（第一次 / 第二次启动）：GPU 进程收到请求到激活 AudioComponentRegistrar 连接 1.830 / 1.774 秒，到创建 SandboxHelper 连接 0.132 / 0.150 秒，SandboxHelper 连接从创建到销毁 0.887 / 0.880 秒，销毁到 `didInitialize` 0.579 / 0.252 秒。都在 4 GiB 的范围附近。
- 观察脚本启动到 GPU 进程出现是 47.8 / 32.2 秒，到首个 GPU 请求是 80.1 / 55.0 秒；4 GiB 同配置（Run132、134、136）的平均值是 53.2 / 34.1 秒和 92.1 / 58.6 秒。启动路径快了约一成，初始化窗口没有跟着变快。
- GPU 进程主线程在包住窗口的 25 秒和 22 秒里用了不超过 1.04 和 1.48 秒 CPU（4 GiB 时是 0.76–1.17 秒）。
- 两次试验都完成了初始化，无响应退出 0 次，诊断点 site0 命中 2 次、site1 0 次。
- Run140 由客体自己关机，控制器记录为客体关机（退出码 0）。这是控制器修正（be94290）之后第一次在真实运行中验证。宿主封装温度最低 53、平均 80.5、最高 92 °C。

### 这一轮顺带得到的两个结果

1. **窗口里 CPU 是饱和的。** 宿主采样显示，初始化窗口内 8 个 vCPU 有约 90% 的时间全部在忙。详见[宿主 CPU 报告](M3-GPU-INIT-HOST-CPU-USE.md)的"结果"。
2. **SandboxHelper 那约 0.9 秒是启动一个新进程的开销，不是固定等待。** launchd 的日志和系统日志给出了第一次试验里这一段的经过（客体时间 08:22:43）：

   | 时刻（秒） | 事件 |
   |---|---|
   | 43.031 | GPU 进程创建 SandboxHelper 连接 |
   | 43.040 | launchd 决定启动 `com.apple.audio.SandboxHelper` |
   | 43.054 | xpcproxy 进程产生 |
   | 43.188 | 换成 SandboxHelper 本体，launchd 记录"已启动" |
   | 43.469 | SandboxHelper 写下第一条日志（动态链接和系统库初始化结束） |
   | 43.566 | 开始编译沙箱配置 |
   | 43.805 | 内核应用沙箱 |
   | 43.815–43.875 | XPC 监听和连接就绪 |
   | 43.918 | GPU 进程收到答复，销毁连接 |

   进程列表里每个 SandboxHelper 实例一生只用 0.58–1.11 秒 CPU（第二次试验的那个是 0.75 秒），与这一段的长度相当，所以这一段是在计算，而不是在等。每个用到音频组件的进程都会启动一个自己的 SandboxHelper，运行结束时系统里有 14 个。

### 证据

- 运行目录：`runs/e05-installed-boot/m3-gpuinit-ram8g-qarma5-20261111-140/`。其中 `guest-uploads/r140logw1.tgz`、`r140logw2.tgz` 是两个窗口的全部进程日志、launchd 日志片段、进程列表和 `memory_pressure` 输出。
- 汇总：`runs/ram-size-gpu-init-20261111/trials-4gib-runs131-137.json`、`trials-8gib-run140.json`，生成脚本在同目录的 `driver/mine.py`。

### 限制

- 8 GiB 只有一轮，两个样本。"没有明显缩短"指的是没有出现足以改变结论的大差别；0.1–0.2 秒的小影响既没有证实，也没有排除。
- 4 GiB 的参照是约 13 小时前取得的。
- 没有做到"完全不压缩"的条件。控制器只接受 4 和 8 GiB。
