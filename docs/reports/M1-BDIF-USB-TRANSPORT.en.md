# M1 / E05: BDIF USB Data Channel and Userspace USB/IP Control Requests

Date: 2026-10-14 (UTC); Master Plan v3, still in M1. Neither AVPBooter acquisition, Apple boot code execution, nor macOS restore occurred in this round.

## From Source Candidate to Executable Verification

Previously, the local BDIF implementation handled only ROOT/AUX disk requests; the USB device ID was defined without an implementation. Candidate source:
https://github.com/steelbrain/experiment-macOS-arm64-on-asahi-linux-arm64/tree/657bb2423ec8d572b22a97dd33563dbba1680e6a

That project's working graphical guest came from a VM pre-installed on a Mac; its README lists native Linux restore separately as an unfinished experiment. Success on another platform is not treated as a completed restore on this Intel laptop.

The original vmapple-usb-chardev.patch is preserved in patches/upstream-reference. An independent sources/qemu-bdif-usb worktree was established without overwriting the existing mainline or exact-clock branches. The pinned modern QEMU was compiled together with the existing VMApple/PAC/clock patches and the candidate USB channel, then tested using self-authored ARM firmware against a Unix socket peer.

## Causal Comparison Before and After Fixes

Among the six tests against the original candidate, only normal and fragmented transfers passed. In the remaining four cases, the guest explicitly reported RX_TIMEOUT:

| Failing case | Source mechanism | Local fix |
|---|---|---|
| 128KiB maximum packet | Receive capacity excluded the 4-byte frame header, preventing the final 4 bytes from entering | Capacity accommodates both the full frame header and payload |
| 16-byte descriptor at end of RAM | Read 128 bytes for debug logging, crossing the RAM boundary even when the descriptor itself was intact | Read only the actual 16-byte descriptor |
| Packet larger than current guest buffer followed by a valid packet | Returned immediately after dropping the first packet, leaving the buffered second packet unprocessed | Process subsequent complete frames within bounds and properly restore read readiness |
| Half-packet disconnect and reconnect | Connection close did not clear stale buffered bytes, causing the next connection to be treated as a continuation of the old packet | Clear per-connection state on OPEN/CLOSED events |

Another runtime issue: qemu_chr_fe_write_all blocks when the peer stops reading. Comparing the same 256-frame payload and QMP operations: the original candidate could not respond to query-status before peer reads resumed, whereas switching to bounded non-blocking writes remained responsive. Once reads resumed, both delivered all bytes intact, showing that the test distinguishes between "eventual data correctness" and "control-plane blocking" rather than merely checking whether the process exited.

## Current Results

- All 16 transport scenarios behaved as expected, covering normal transfer, fragmentation, coalesced packets, maximum RX, maximum TX, zero-length transfer, descriptor boundary, invalid DMA, oversized TX, no DMA when no buffer has been submitted, no-data negative case, half-packet disconnect/reconnect, oversized-frame rejection with reconnect, and ROOT/AUX read regressions.
- Maximum RX: 131072 bytes; TX limit: 4096 bytes, without expanding the candidate protocol.
- Backpressure: 256 frames of 4096-byte payload each plus a 4-byte header, totaling 1049600 bytes, matched completely; QMP on the fixed implementation remained responsive while the peer paused reading.
- Rerunning 5 timer/GIC/MMU/combined/negative scenarios on the same new QEMU binary behaved as expected; platform paths remain operable when no USB backend is configured.
- The recorded patches reconstruct all 11 modified files identically from the pinned QEMU commit. This proves source-patch persistence only and does not claim full dependency reproducibility on a clean host.

## One Layer Higher: USB/IP Control Requests Traversing the Actual Guest

Using the official Linux USB/IP wire format:
https://docs.kernel.org/usb/usbip_protocol.html

The current chain is: **userspace USB/IP client -> socketpair control gateway -> AVP length-prefixed Unix channel -> QEMU BDIF -> self-authored ARM guest -> returned response**.

Rather than replacing the guest with a Python mock, 64 bytes of control OUT data are stored by the ARM program itself and retrieved via an independent IN request. Device descriptors are generated by that ARM program using an explicit synthetic test identity without impersonating Apple DFU. Status bytes also originate from the guest.

Across three scenario groups, all 12 checks behaved as expected: descriptor, control IN/OUT, raw data readback, normal status, empty status preserved as empty, guest STALL, malformed reply returning EPROTO, and silent reply returning ETIMEDOUT. After negative cases finish, the test harness actively terminates the test QEMU instance rather than counting termination as a guest pass.

**Key distinction: timeouts or empty packets are NOT automatically synthesized into DFU download completion or WAIT_RESET.** Upstream experimental bridge scripts include that inference, which this project does not adopt. An empty IN response has an actual length of 0 and is not padded into a 6-byte success status; whether real restore tools handle this properly requires empirical testing.

This gateway supports only serial OP_IMPORT and EP0 control transfers, excluding DEVLIST, non-zero endpoints, isochronous transfers, asynchronous multi-request handling, and UNLINK cancellation; vhci-hcd was not loaded, no host USB device was attached, and idevicerestore was not executed.

## Fix and Experimental Boundaries

This is neither a complete USB controller nor a reliable restore engine. Unverified items remain, including descriptor chains, real firmware ABI semantics, peer frame coordination across reset, transaction IDs, post-timeout recovery policies, migration, and full lifecycle behavior. Current reset cleanup guarantees only local software-state reset and cannot claim synchronized reset of an external peer.

Low-level DMA, transfer completion, USB control responses, DFU protocol state, signature verification, and AUX/OS installation are distinct layers. This round closes self-authored experiments on the lower layers without conflating them with a successful macOS restore.

## Impact on the Plan

E05 advances from "apply-check only on a candidate patch" to "locally executable BDIF + userspace EP0 transport prototype." The next priority is acquiring a matching AVPBooter to observe real boot-firmware USB descriptors and requests before deciding when to connect Linux kernel USB/IP and restore utilities. Properly initialized AUX storage, VM identity, system disk, and signing materials remain M2 prerequisites.
