## Offline CPU-occupancy analysis (2026-11-01)

`experiments/E05-installed-boot/cpu_occupancy.py` reads only the retained `results.json`, `host-qemu-thread-samples.log` and `current-process.jsonl`; no VM was started. Host utilization is the per-interval delta of the cumulative `TIME` column (1 s resolution over ~30 s intervals). Guest occupancy treats the most common `kernel_task` PC (`0xfffffe0028f0d434`) as the idle loop. Outputs: `runs/m3-run68-cpu-occupancy-20261101.json` (00:14:00Z–00:45:00Z, login through Apple-menu shutdown) and `runs/m3-run68-cpu-occupancy-safari-window-20261101.json` (00:19:30Z–00:29:00Z, Safari start through the GPU PID 630 exit check). UI journal times: login submitted 00:14:23Z, Safari start 00:19:32Z, GPU-exit capture 00:28:50Z, shutdown menu 00:40:58Z.

- **Host:** across the 61 intervals from 00:14Z to 00:45Z, the eight `CPU n/TCG` threads together used 4.99–6.75 host cores (median 6.05); the busiest single vCPU reached 86% of a core; `reims-vgpu`/`metal2vulkan`/`[vk*]` threads together used at most 0.10 core. The step up from 3.06–3.63 cores happened at 00:14:19Z, at login and before Safari started. In the Safari window the vCPUs used 5.12–6.59 cores. The last two intervals (00:44:53Z–00:45:53Z) fell to 3.29 and 1.46 cores. The host has 20 logical CPUs, so QEMU was not host-CPU-limited.
- **Guest:** from 00:14Z to 00:45Z, 4 of 464 sampled CPU slots (58 pauses × 8 CPUs, ≈1%) were at the idle PC and 23 (≈5%) were `kernel_task` at any PC, versus 110 of 224 (49%) idle before 00:14Z. In the Safari window, 0 of 144 slots were idle; the most frequent were `sirittsd` 11, non-idle `kernel_task` 9, `WindowServer` 8, then `homed`, `eligibilityd` and `siriactionsd` at 5 each (16-byte comm names as recorded). Across 00:14Z–00:45Z the leading names were `sirittsd` 23, `WindowServer` 17, `Siri AI` 16, `com.apple.AppleU` 13, `XProtectRemediat` 13, `launchd` 12, `homed` 11, `log` 11, `BackgroundShortc` 10, `softwareupdated` 9 and `system_profiler` 9; 229 of 460 busy slots were EL0.
- **WebKit:** GPU PID 630 was never sampled on-CPU. `com.apple.WebKit` PIDs changed from 602 (00:17:21Z) to 849/852 (00:25–00:26Z) and 928/927 (00:30–00:32Z), consistent with process relaunches; the samples alone do not show exit reasons.
- **Interpretation:** the GPU-process failure window coincides with saturated guest vCPUs dominated by session background daemons, while host graphics threads were idle. This favours CPU starvation of the WebKit GPU process as the first hypothesis to test. The 30 s point samples cannot exclude a Metal/vGPU IPC wait or a watchdog-policy cause, and part of the later load was diagnostic: the `log` process is most likely the Terminal `log show` query run from 00:29Z.

## Limits and next step

This run establishes correlation between WebKit GPU PID disappearance, prolonged guest↔vGPU/display cadence loss, and a later guest shutdown stall. It does **not** identify whether the initiating fault was CPU starvation, Metal/vGPU IPC, watchdog policy, or another WebKit cause; the offline analysis above makes guest CPU starvation the first hypothesis to test. No second clean Safari rerun was attempted after Run68. A future rerun should first let post-login background work settle or reduce it (for example Siri and automatic-update services), add a bounded in-guest log export, and repeat the same PID/thread plus host vGPU sampling at a finer interval.
